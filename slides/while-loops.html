Until It’s True

Session 5 · Lesson D3, part 1 · Robot Rockstars · SPIKE Prime + Pybricks

2026-09-28

A. The Question

Some jobs have no fixed time. Only a finish line. 🏁

Drive until the black line

left.run(300)
wait(????)     # how long??
left.stop()

How long do you wait before stop()?

Nobody knows. So don’t guess: keep checking. Keep driving while the line is not there yet.

The robot’s eye comes later. Today the finish line is a wheel angle.

Let them answer with a number first. Someone will say “2000”, someone “3500”. Ask: what if the robot starts further back? What if the battery is low? The time changes every run, so no number is right. That is the whole reason while exists: it repeats until something becomes true, however long that takes. Keep this slide to two minutes. This session assumes only D2 (imports, Motor, run_angle, variables). The next slide hands them the five motor words the loops need, and no for loop is needed anywhere; for arrives in Drive a Square.

Five new words 🔤

Code What it does
left.run(300) start turning at 300 °/s, and keep going
left.stop() stop turning
left.reset_angle(0) call this spot 0°
left.angle() how far it has turned since 0°
print(x) show x in the console

run_angle stops by itself. run never does. Something else has to call stop(), at the right moment.

Two minutes, no robots yet. run_angle from D2 is “go this far, then stop”; run is “go, and I will tell you when to stop”. That missing “when” is the whole session. print is new too: point at the console pane in the Pybricks editor so they know where the numbers will appear. If someone asks how run_angle knows when to stop: “it runs a loop just like the one you are about to write”. That is true, and it is a good hook.

B. Watch a Loop Think

Step through it one line at a time. 👣

Meet while

Predict: how many lines will it print? Then press Step.

count = 0
while count < 3:
print(count)
count = count + 1
print("done")
check: not yet
count ?body ran 0 times

Check → body → jump back → check again. It leaves the moment the check says False.

Collect predictions on the board before anyone presses anything: “3”, “4”, “2” are all common. Then Step slowly and have the room say each line out loud before you press. The lamp on the right is the heart of it: every time the highlight lands on the while line, the check is asked again and the lamp shows the answer. Point out the jump back up after count = count + 1, which is the only thing that makes a loop a loop. It prints 0, 1, 2, then “done”: four lines, and the body ran 3 times. The fourth check is the one people forget: it is the False that lets the program leave.

How many times?

Change the number. Predict the prints first.

·
count = 0
while count < 3:
print(count)
count = count + 1
print("done")
check: not yet
count ?body ran 0 times

With < 0 the body runs zero times. The check always comes first.

Go < 5 first (easy win: five prints), then < 0. Most students predict one print for < 0 because “the loop runs at least once”. It does not: the very first check is 0 < 0, which is False, so Python skips the body and goes straight to “done”. Say the rule: a while asks before it acts. This matters on the robot: if the wheel is already past the finish line, a while drive does nothing at all, which is correct.

🐛 Bug hunt: the missing colon

This loop won’t even start. Pybricks flags the first line in red. What’s missing?

count = 0
while count < 3
    print(count)
    count = count + 1

SyntaxError: no colon. Every loop header ends in :, which says “the block starts here.” Fix: while count < 3:

The colon is invisible until it’s missing. Type it live so the red SyntaxError lands on the while line. Make the habit loud: say “colon” out loud every time anyone types a loop header this week. It is the number-one typo of the session, and for will have exactly the same rule in Drive a Square.

🐛 Bug hunt: the runaway line

The colon is back, and it still won’t run. The error points at line 3.

count = 0
while count < 3:
print(count)
count = count + 1

IndentationError: lines inside a loop must be pushed in (one Tab). The spaces tell Python what repeats.

Indentation-as-meaning is the single biggest beginner hurdle, so spend a beat. Show flush-left (crashes) next to indented (runs). Then the sneaky version: indent only print(count). No crash, but count = count + 1 now sits outside the loop, so the body never changes what the check reads. That is exactly the next slide, so let the frozen console land and go straight on.

Break it: the loop that never ends 🥶

Delete one line. Predict, then Run.

·
count = 0
while count < 3:
print(count)
count = count + 1
print("done")
check: not yet
count ?body ran 0 times

The check reads count. Nothing changes count. The body must change what the check reads.

Run it once with the line in place (it ends), then delete it and run again. Let it spin: the counter races, the console floods with 0s, and the check number climbs into the hundreds. Ask: “when will it stop?” (Never.) Press Stop and tie it to the hub: on the robot, the centre button is your Stop. Then the rule on the card. Every frozen loop they will ever write breaks this rule: the check is waiting for a change that nothing in the body makes. On the robot, the “change” usually comes from the world: a wheel turning, a gyro moving. That is the next section.

C. Now With a Wheel

Same loop. Now the check reads a motor. ⚙️

Drive to the finish line 🏁

Two full turns = 720°. Where will the wheel stop?

left.reset_angle(0)
left.run(300)
while left.angle() < 720:
wait(10)
left.stop()
angle 0°checks 0
check: not yet
0°720° 🏁1000°

Same four ideas as the counter: something to read (left.angle()), a check (< 720), a body (wait(10)), and a change. The difference is who makes the change: not a line of code, but the motor, which keeps turning on its own because left.run(300) started it before the loop. The body only waits. Each dot on the track is one check, and at wait(10) they are so close together they look like a solid line. It stops at 720 exactly. Keep that number in mind: slide 3 of this section breaks it.

Break it: the wheel that never moves 😴

Someone deleted a line. What happens now?

·
left.reset_angle(0)
left.run(300)
while left.angle() < 720:
wait(10)
left.stop()
angle 0°checks 0
check: not yet
0°720° 🏁1000°

No run, no turning. left.angle() stays 0, so the check stays True forever. Same bug as the counter.

This is the robot version of the frozen counter, and it is the most common real bug of the week: the program “hangs”, the robot sits still, and students think the hub crashed. It did not crash; it is checking hundreds of times a second, and the answer never changes. Ask “what should change the angle?” and let them find the missing run. On the real hub, the centre button stops it.

Break it: the check only happens at the top ⏱️

Make the wait longer. Predict where it stops.

·
left.reset_angle(0)
left.run(300)
while left.angle() < 720:
wait(10)
left.stop()
angle 0°checks 0
check: not yet
0°720° 🏁1000°

The loop only looks at the top. Between checks the wheel keeps going. Short wait, sharp stop.

Take a prediction for each wait before running it. Most students expect every version to stop at 720, because “the code says 720”. Run 10 ms (720), then 250 ms (750, 30° late), then 1000 ms (900, a full 180° late). The dots on the track are the only moments the loop was looking: at wait(1000) it checks at 0, 300, 600 and 900, and it cannot notice the finish line in between. The check only happens at the top of the loop, and a long body means long blind spots. That is why every robot loop in this course keeps its body short, wait(10) or less. The sim ignores momentum on purpose; the bench slide brings it back.

D. On Purpose

One loop that never ends on purpose, then your own wheel. ♾️

Forever, on purpose ♾️

while True:
    print(left.angle())
    wait(100)

True is a check that can never be False. The hub’s centre button ends it.

Patrols and line followers work this way: keep going until a human says stop.

Short slide. The frozen loops earlier were accidents; this one is a choice. It is also the best debugging tool they have: run it, turn the wheel by hand and watch the angle stream. Have one student try it on a robot now if time allows. Later decks (line following, patrol) put real work inside while True.

Bench: stop at one turn 🤖

from pybricks.pupdevices import Motor
from pybricks.parameters import Port
from pybricks.tools import wait
left = Motor(Port.F)     # yours
left.reset_angle(0)
left.run(300)
while left.angle() < 360:
    wait(10)
left.stop()
wait(500)
print(left.angle())
  1. Run it. What does it print?
  2. Make it 3 turns.
  3. Halve the speed. Does the extra shrink?

The sim stopped right on the line. Yours went past. The loop caught 360 on time, so who stole the extra degrees? Hold that thought for Drive a Square.

Robots out, one wheel lifted off the table or the robot on its back so it does not drive away. Expect prints like 370 to 390 at speed 300: the loop caught the finish line within a few degrees, then the wheel coasted. The wait(500) before the print lets the coast finish, otherwise they read the angle mid-coast. Halving the speed should shrink the extra, which proves it is not the loop. Coach knowledge only: it is momentum. Do not name it today. Drive a Square names it on the gyro (“it printed 94, who’s guilty?”), and that reveal only works if the room has not heard the word yet. If a team gets a frozen program, send them back to the two “break it” slides: is the check reading something that changes? Port F follows the course robot; students change it to match their own build. Direction is left out on purpose: a lone wheel counts positive degrees for run(300) whichever way it is mounted.

You’re done when…

Done when

  • You can predict how many times any while body runs (zero counts)
  • You can fix a loop that never ends, and say what never changed
  • You can fix a missing colon or a runaway line
  • Your wheel stops at one turn, and you can say the extra is not the loop’s fault

Check each leg orally at the bench. For leg one, write while count < 4: with count = 1 on the board and ask for the number of prints (3). For leg two, show a while left.angle() < 360: wait(10) with no run above it and ask what is wrong. For leg three, hand them a header with no colon and a body typed flush-left. For leg four, ask why the printed angle is bigger than 360: “the wheel kept going after stop()” is a pass; the word momentum waits for Drive a Square.
