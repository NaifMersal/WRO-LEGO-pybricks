Every file was tuned for a robot that just became a parts donor. The facts (wheels, ports, gains, speeds) are scattered across files and functions, so a robot swap means twenty hunted edits, and missing one means the robot lies quietly. The facts need one home.

Make it concrete with the team’s actual files if the draft order allows — three real constants blocks on screen beats the mock-up. Sharpen the sting: it’s not just today’s merge. The donor pool means a swap can happen again mid-season (a cracked chassis at Week 4 pace), and next time there’s no afternoon to spare. Elicit the shape of the fix before naming it — they’ve done this twice: constants block (square day), library module (consolidation day). Same instinct, one level up: promote the constants to a single shared object the whole team’s code reads.

Fix it: ROBOT FACTS, the robot in one place

# movements.py -- ROBOT FACTS. The only place a number about the robot lives.
LEFT_MOTOR_PORT  = Port.F     # yours; re-port a motor = one edit
RIGHT_MOTOR_PORT = Port.B     # yours
EYE_PORT         = Port.D     # yours

LEFT_DIRECTION  = Direction.COUNTERCLOCKWISE   # flip if it reverses  TUNE
RIGHT_DIRECTION = Direction.CLOCKWISE                             # TUNE

WHEEL_DIAMETER = 88           # mm, MEASURE the team robot        TUNE
AXLE_TRACK     = 128          # mm, wheel centre to centre        TUNE

CRUISE_SPEED   = 300          # mm/s
LINE_THRESHOLD = 50           # halfway between black and white  TUNE
KP_LINE        = 1.2          # how hard to steer back to the line TUNE

One block at the top of the file, a name on every line, TUNE on everything you must measure. Nothing further down is allowed to know a number about the robot. It reads the block. Same instinct you’ve used twice already, one level up.

No classes today, and none this season — a plain block of named constants does the whole job, and every student can already read one. Walk the categories: ports, geometry, tuned knobs — point out these are exactly the numbers that differed across the three files on the last slide. Make TUNE the habit: it marks every value that must be measured on this robot, so a squad scanning the block knows exactly what a robot swap costs them. The full gold-reference block is in code/movements.py; teams copy it and edit their measured values.

Every verb reads the block

# movements.py -- the verbs READ the block, they don't hide numbers
left_motor  = Motor(LEFT_MOTOR_PORT, LEFT_DIRECTION)
right_motor = Motor(RIGHT_MOTOR_PORT, RIGHT_DIRECTION)

robot = DriveBase(left_motor, right_motor,
                  WHEEL_DIAMETER, AXLE_TRACK)

def drive_straight(distance_mm, speed=CRUISE_SPEED):
    robot.settings(straight_speed=speed)
    robot.straight(distance_mm)

New robot? Measure it, edit the block, done. The library and every mission file never change, and the donor pool just became a one-line insurance policy. 🛡️

The team exercise that proves it (from the exemplar): run the merged code with teammate A’s old constants on the chosen robot — watch the square miss; then fix ONLY the ROBOT FACTS block and rerun — the square closes. One file changed, zero functions touched. That felt difference is the lesson. Also flag the discipline cost honestly: from today, hard-coding a number inside a function is a team foul — a merge conflict waiting to happen. The constants block habit from the library days is what made this promotion cheap. Continuity note: squads’ own movements.py from D5 may still spell the turn knob gain= — fold the rename into today’s promotion and say it once: “we’ve been calling this knob the gain; its code name is kp, same K-family as the KP constants.”

C. The Reveal: Let DriveBase Drive

You built gyro turns, self-healing straights, and all three letters of P·I·D by hand, from raw motors. Now meet the pro version that’s been in the box all along. 🎁

You built a robot driver 🏆

You wrote, these two weeks

  • your turn verb, a PD turn that watches itself, brakes before it arrives, and lands true
  • drive_straight(distance), a self-healing straight with a finish line in degrees

Every WRO robot needs

  • turns that are true, not “about right”
  • straights that survive bumps, seams, and battery moods

Pybricks ships both moves, polished and tested, inside one tool: DriveBase. It runs a professional P·I·D on every move, and you’ll understand every letter of it, because you spent two weeks building all three.

This is the payoff the whole fortnight has been walking toward — let it feel like a gift, not a rug-pull. The frame that keeps their work dignified: professionals don’t hand-roll what a trusted library ships, but they can only trust it because they know what’s inside — and this room now does. If anyone asks “why didn’t we start here?”: because then DriveBase would be magic, and magic can’t be debugged at a competition table. Nothing they built was wasted — the next slides show exactly which verbs survive.

Measure your robot first

DriveBase asks for two numbers: wheel diameter and axle track (tire-center to tire-center). Why does it need the second one?

Hint: you already used it once, back when you drove a square…

It’s your turn-circle! You ran that math by hand once to get 131, and DriveBase runs your derivation for any angle. The shortcut is math you already own.

Both numbers are measured, not copied: roll the wheel 5 turns, divide by 5 and π for diameter (they’ll land near 88); the track they measured on Day 3 for the 131 derivation (≈128 mm on the coach’s build; the stock ADB is ≈114) — have each team re-measure its chosen robot now, since that’s the number going into its config. Wrong track → every turn systematically over- or under-shoots: that’s the afternoon’s tuning conversation (robot.settings()). If asked why the track matters: a spin-in-place drives the wheels around a circle as wide as the axle track — wider track = more wheel-degrees per robot-degree.

Build your DriveBase from the block

from pybricks.robotics import DriveBase   # now earned

robot = DriveBase(left_motor, right_motor,
                  WHEEL_DIAMETER, AXLE_TRACK)
robot.use_gyro(True)  # your gyro + full PID, switched on
robot.settings(straight_speed=CRUISE_SPEED)

DriveBase speaks mm and robot-degrees, as in robot.straight(300) and robot.turn(90). With use_gyro(True) every move is watched and PID-corrected, exactly like yours were. Its two constructor arguments are the two facts you measured: wheel diameter and axle track.

✂️ Now delete your turn verb

Your turn(angle, absolute=False) from the library days. Here is Pybricks’:

robot.turn(angle, then=Stop.HOLD, wait=True, absolute=False)

The same word, the same default, the same meaning: robot.turn(90) spins 90 more, robot.turn(90, absolute=True) faces 90. You didn’t guess it, you re-derived it, because it’s the only sensible way to say it. (Pybricks puts absolute last, after then= and wait=, so always name it: absolute=True, never a bare True.)

So the verb goes. A function that only re-spells a built-in is one more name to maintain, so delete it and call robot.turn(). movements.py keeps the verbs that do real work: drive_straight, find_line, follow_line, drive_to_wall, wall_square, square_on_line.

This is the moment the fortnight pays off twice — don’t rush it. Put their D5 turn on screen beside the Pybricks line and let the room notice the match before you say it; the “we invented the same thing” feeling is what makes the deletion satisfying instead of deflating. Then make the rule explicit and general, because it governs every file they write from here: a wrapper has to earn its name. If a function only renames something Pybricks already gives you, it is one more thing to keep in sync and one more name for a teammate to learn — delete it. If it holds real logic (hunting a line, feeling a wall), keep it. Same test kills the heading() wrapper someone always proposes: robot.angle() already says it. Expect one squad to object that “our name is friendlier” — the answer is that the friendly name is now wrong half the time, because theirs took no then= or wait=. Land the positional trap explicitly, because it bites silently: in their version absolute was the 2nd argument, in Pybricks’ it is the 4th, so robot.turn(90, True) sets then=True and turns relative anyway. The habit that makes it a non-issue is one they already have from speed= and kd= — name the argument.

What retires, what stays yours

Retires today 🪦

  • your turn verb → robot.turn(…)
  • the hand-tuned turn kp/kd → DriveBase’s own PID
  • hub.imu.reset_heading(0) → robot.reset(angle=0)

Stays in movements.py 💪

  • drive_straight(), new insides and the same name
  • drive_to_wall() · wall_square(), the feel verbs
  • follow_line() · square_on_line(), the eyes verbs
  • every mechanism verb Week 3 will add

DriveBase replaces the moving and nothing else. It has no idea how to feel a wall, ride a line’s edge, or work a mechanism. From here on: DriveBase drives, your library does the rest.

This boundary slide is the anti-demoralizer — put numbers on it: two verbs retire, five survive today, and every mechanism verb from Week 3 joins the surviving side. Be precise about how they retire, because the two cases differ. drive_straight keeps its name: it still does real work (it sets the speed, then drives), so its insides swap to robot.straight() and every mission list runs unchanged — that’s the payoff of naming moves, swap the engine and keep the verb. The turn verb is the other case: robot.turn() already takes the same absolute flag, so wrapping it would add a name and nothing else — it is deleted, not rewrapped. robot.stalled() upgrades the inside of drive_to_wall without changing its name, same as drive_straight. Name one more so nobody is surprised later: square_on_line changes shape inside. The version they wrote on the line day drives both wheels and lets each one park itself the moment its own eye crosses — which works because those were two independent motors. Once the motors belong to a DriveBase, starting one stops the other, so the library version creeps until either eye finds the line and then pivots to bring the second one on. Same verb, same reason it needs two eyes, different insides — and that difference is itself the lesson about what you traded away for DriveBase’s gyro. Last, the zero: from today hub.imu.reset_heading(0) is the wrong verb — DriveBase owns the gyro now, so robot.reset(angle=0) is what says “this way is zero”, and it moves the gyro and the odometer together. Say it out loud, because every program they wrote in the last fortnight opens with the old line, and a squad that keeps it ends up with two zeros that disagree.

D. Draft Day

Today’s showdown: Mini Mission 🎤, then the draft.

Mini Mission 🎤

The challenge

A 3-task run (drive, turn, push an object home) in 60 seconds. Everything from two weeks on one clock: integration, time management, nerve.

  • Plan it as a sequence of your verbs, written out longhand. The list that walks itself is still ahead of you.
  • Budget the clock: a clean 2-task run beats a chaotic 3-task attempt. (Sound familiar? It’s the anchor-first rule, in miniature.)

Template is Competition Ready Lesson 8 “Mission Ready.” This is the last solo competition and the scorecard’s final data point — watch integration and composure, not just score. Call out anyone who deliberately drops to two tasks to bank clean points: that’s competition maturity, praise it loudly — it’s the exact instinct the anchor-first strategy needs from them in Week 4. After scores are recorded, close the leaderboard era warmly: from tomorrow the competition is team vs team.

The draft 🤝

  • Teams are formed on who works well together and what each team needs. Complementary skills beat matching skills.
  • Each team reviews its members’ robots and selects one as its competition robot.
  • The unselected robots become the parts donor pool, your insurance one config edit away. 🛡️
  • From tomorrow: team vs team, every day, which doubles the mat time.

Your robot may retire to the donor pool. Your code and your skills don’t. Everything merges onto the team robot through one ROBOT FACTS block, and both of the team’s cross-trained roles need every verb you built. The draft picks a chassis, not a coder.

Say the framing line exactly as planned and nothing more: “I’m teaming you based on who works well together and what each team needs” — never rank, never “you scored lowest.” The pairings are already decided from the private scorecard + library benchmarks; announce, don’t debate. Give the selection its dignity: each team physically inspects its candidate robots (the four quality checks from Day 1 make a nice ritual return) before choosing. Handle the sting of an unselected robot with the card’s line — the donor pool is genuinely valuable, not a consolation. Set up team build areas after the announcement.
